# LLM Framework Setup Launcher

The setup launcher is a standalone local desktop application for installing and
starting LLM Framework. It is intentionally separate from the FastAPI backend
and Next.js frontend: neither the model nor a remote client can invoke its host
operations.

## What it does

1. Detects the operating system, Docker CLI, Docker Compose, Docker service,
   Ollama CLI/service, available ports, disk space, and existing configuration.
2. Offers explicit prerequisite installation:
   - Windows uses fixed `winget` package IDs after showing the exact command and
     obtaining confirmation.
   - macOS uses fixed Homebrew casks when Homebrew is available, after showing
     the exact command and obtaining confirmation.
   - Linux opens Docker's and Ollama's official instructions because supported
     repositories, package names, init systems, and elevation differ by
     distribution. It never pipes a remote script into a root shell.
3. Lets the user choose native, bundled, or remote Ollama.
4. Generates cryptographically random PostgreSQL and recovery access secrets.
5. Preserves an existing `.env` by default. Replacement requires confirmation
   and creates a timestamped, owner-restricted backup.
6. Starts PostgreSQL and the chosen Ollama arrangement, pulls local models,
   builds the application, and verifies the backend, frontend, and the
   backend-to-Ollama connection.

Python, Node.js, PostgreSQL, pgvector, and application libraries are inside the
Docker images and do not need to be installed on the user's host.

## Install from a GitHub release

Ordinary users do not need Git, GitHub Desktop, Python, or a source-code clone.
On the GitHub repository page, open **Releases**, choose the release marked
**Latest**, expand **Assets**, and download the ZIP for the operating system.
Extract the complete ZIP before opening the launcher; it verifies and operates
on the application files packaged beside it.

See [Download and install](../docs/download-and-install.md) for the user-facing
steps and platform-specific notes.

## Run from source

Python 3 with Tk support is needed only when running the launcher from source:

```bash
python3 setup_launcher/main.py
```

The packaged GitHub releases bundle Python and Tk. Extract the platform bundle
and run `LLM-Framework-Setup` from the repository root:

- Windows: `LLM-Framework-Setup.exe`
- macOS: `LLM-Framework-Setup.app`
- Linux: `LLM-Framework-Setup`

On macOS, release distribution should be code-signed and notarized. On Windows,
the executable should be Authenticode-signed. The build workflow deliberately
does not invent signing credentials: unsigned CI artifacts are suitable for
testing, while signed public releases require repository secrets and a
maintainer-owned certificate/notarization workflow.

## Ollama choices

### Native

Recommended on macOS and Windows when native accelerator support is wanted.
The containerized backend connects through
`http://host.docker.internal:11434`. Linux is supported through Docker's
`host-gateway` mapping when native Ollama is deliberately selected.

### Bundled

Starts the Compose `ollama` service and stores models in the `ollama_data`
volume. The base Compose file does not promise GPU acceleration. NVIDIA users
can later use the documented GPU overlay after installing the required runtime.

### Remote

Accepts an explicit `http://` or `https://` endpoint, rejects embedded
credentials and non-HTTP schemes, and tests it before changing configuration.
The remote host must already contain the selected models. Framework prompts are
sent to that endpoint, so it is not a local-only configuration.

## Security boundary

- Commands are fixed argument arrays executed without a shell.
- User-entered model tags are restricted before becoming command arguments.
- Command time and captured output are bounded.
- Secrets are generated by the operating system CSPRNG, never command-line
  arguments, and never written to the progress log.
- Local `.env`, backups, and temporary files are ignored by Git.
- The launcher exits after setup and creates no privileged service.
- The Docker socket is never mounted into the backend or frontend.
- The normal application exposes no package-install or host-command API.

The access token is copied only after an explicit button press. Clipboard
contents remain the user's responsibility and should be cleared after storing
the token securely.

## Failure and retry

Each failure identifies the stage and one next action. Safe completed work—such
as downloaded images, model layers, volumes, and configuration—is retained for
retry. The launcher does not delete containers, volumes, models, documents, or
databases.

Moving the repository or launcher does not move existing Docker volumes,
documents, database contents, or Ollama models. Backup and migration remain a
separate deliberate operation.

## Tests

```bash
PYTHONPATH=setup_launcher python3 -m unittest discover -s setup_launcher/tests -v
```

Tests use temporary folders and mocked infrastructure. They do not install
packages, start Docker, change the developer's `.env`, or pull models. Real
installation acceptance tests must be supervised on disposable Windows,
macOS, and Linux machines.

## Build artifacts

Install the pinned build dependency and run PyInstaller from the repository
root:

```bash
python3 -m pip install -r setup_launcher/requirements-build.txt
python3 setup_launcher/generate_integrity_manifest.py
python3 -m PyInstaller --noconfirm --clean setup_launcher/macos.spec
```

That command creates a versioned universal Intel/Apple-silicon macOS `.app`
bundle. The workflow uses the Windows version resource and adds `--onefile` on
Windows/Linux to create a single executable. One-file macOS application bundles
are intentionally avoided because they conflict with platform signing and
notarization expectations.

The GitHub Actions workflow performs this independently on each supported
runner and packages a clean `git archive` of the production repository with the
matching launcher artifact. It never includes the working tree's `.env`, model
files, database data, caches, or untracked local workspaces.

Packaged launchers embed a SHA-256 manifest of every Docker Compose,
backend-image, and frontend-image build input. Setup refuses to execute Compose
against missing or modified production inputs. Source-mode runs are clearly
reported as development mode because they have no signed/embedded manifest.
